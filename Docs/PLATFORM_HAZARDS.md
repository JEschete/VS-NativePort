# Platform hazards

Every place the port may depend on something PS1 hardware tolerated and this platform does not. It exists so that #251
is the last crash of its kind that a player finds first. [HAZARD_LEDGER.csv](ledgers/HAZARD_LEDGER.csv) has one row per
site. `tools\ledger\hazards.py` keeps it current, and CI fails on a new site until someone fixes or acknowledges it.

## What the problem actually is

The original runs on a 32-bit MIPS PS1, and the port runs on x64 Windows. **Going back to a 32-bit build would not help.**
#251 happened because address 0 is readable RAM on a PS1, so a read through an empty pointer returned bytes and play
went on. Address 0 faults on 32-bit Windows too. Most of the classes below are PS1 hardware differences; only
`POINTER-INT`, `BYTE-OFFSET` and `LITERAL-SIZE` are about pointer width.

The fixes below move the code forward, so nothing here needs the old platform's behavior to come back.

## Reading the ledger

| Column | Meaning |
| --- | --- |
| `class` | Hazard class, explained in the tables below |
| `evidence` | `compiler`: clang reported it in a real build. `pattern`: found by reading source |
| `confidence` | `high` for compiler rows. `medium` for an unchecked variable or expression. `low` where a fixed index or an ambiguous literal makes a problem less likely |
| `function`, `symbol` | Catalog ID and native name, which join to [MODERNIZATION_LEDGER.csv](ledgers/MODERNIZATION_LEDGER.csv). Blank for data, types and helpers outside the catalog |
| `issue`, `imp_step` | The roadmap issue and step whose work should absorb the fix (proposed mapping) |
| `status`, `notes` | The only hand-written columns |

**A pattern row is a candidate, not a proven bug.** The scanner reads one function at a time, so it cannot see a check made
by a caller. It found the real #251 site, and spot checks by hand found both real problems and false alarms.

### Triage

| Status | Use when |
| --- | --- |
| `open` | Not reviewed yet |
| `guarded` | A check exists that the scanner cannot see. Say where |
| `fixed` | Fixed, but the pattern remains. Name the test |
| `false-positive` | Cannot happen. Say why |
| `accepted` | Real and deliberately left. Say why |

Any status except `open` needs a note, and the check rejects one without it.

**Before adding a null check, decide whether empty is a valid state.** A gimmick actor really has no record, so a check was
the right fix for #251. A stale pointer is a different bug: #182 was a pointer half-cleared by an `int*` write, and a check
there would have hidden the defect and left the wrong behavior in place.

| `ALWAYS-TRUE-GUARD` | The check was harmless. An original address could be any value. | The check is meaningless, so it cannot stop a bad read. | Test the state that is actually in doubt, such as an optional or a validated handle. |
| `DIV-ZERO` | `div` does not trap in hardware. The original compiler may have added its own check, so confirm per site. | Integer division by zero, and `INT_MIN / -1`, raise an exception and end the process. | A `FixedDivide` helper with one written-down result for a zero divisor, or a `Fixed12` type carrying it. |
| `UNINITIALIZED` | Whatever the register or stack held, often the same each run, so it could look reliable. | A different value by build and run, and undefined to the optimizer. | Initialize at declaration. Where the old value mattered, name that value explicitly. |
| `RETURN-FALLOFF` | The caller reads whatever `$v0` last held. | The caller reads whatever `eax` holds, a different value from the same code. | Return the intended value, or make the function `void` if nothing uses it. |

| `PS1-ADDRESS` | RAM and the scratchpad sit at known addresses. | That address means nothing here, and reading it faults. | A named owning object or a resource ID. Keep original addresses in the import boundary only. |

## Release keeps its checks

Copied code now compiles with these two flags, alongside `-fno-finite-loops` and `-fno-strict-return`:

| Flag | What it preserves |
| --- | --- |
| `-fno-delete-null-pointer-checks` | A null check after a read stays in the program |
| `-fwrapv` | Signed overflow wraps, as it did on the PS1, so an overflow check stays in the program |

Without them, compiling at `/O2` removed `if (table[i] == nullptr)` after a read of `table[i]->a`, and `if (x + 1 < x)`. With
them, all three test functions keep their comparisons. Strict aliasing is not a concern, because clang-cl already passes
`-relaxed-aliasing`.

With the flags, Debug and Release pass every test and match the same replay baselines, so gameplay on those scenarios did not
change. They apply to sources using `VSCopiedCOptions`, not to strict C++ sources, which should not rely on either behavior.
These flags keep a check that the source already has. They do not add one, so `GUARD-AFTER-READ` sites still need fixing.

## Modern replacements

### Empty slots: `NULL-TABLE`, `NULL-RETURN`, `GUARD-AFTER-READ`

```cpp
// Today (the #251 shape): nothing says this slot can be empty.
Actors_ActorRecord* actor = Actors_actorRecords[actor_slot];
if (actor->instance.weaponDrawn) { ... }

// Modern: a typed ID, and a lookup whose result cannot be used without handling the empty case.
enum class ActorId : std::uint32_t {};

class ActorRegistry {
 public:
  [[nodiscard]] std::optional<std::reference_wrapper<ActorRecord>> Find(ActorId id);
};

if (const auto actor = actors.Find(id); actor && actor->get().weapon_drawn) { ... }
```

Pass `ActorRecord&` once a value is known to exist, so a function's signature says it cannot be empty. A gimmick and an actor
with a body are different things, so `std::variant<ActorBody, GimmickBody>` can make the gimmick case impossible to forget.
This work belongs to #55 and #57.

### Division: `DIV-ZERO`

```cpp
// One written-down answer instead of a crash, and one place to change it.
[[nodiscard]] constexpr std::int32_t DivideOrZero(std::int32_t value, std::int32_t divisor) {
  if (divisor == 0) return 0;
  if (value == std::numeric_limits<std::int32_t>::min() && divisor == -1) return value;
  return value / divisor;
}
```

Zero is only an example, and the right answer depends on the site. PS1 `div` does not trap, but the original compiler often
added its own check that raised an exception, so read the original assembly before choosing. `Fixed12` from
[plan section 8.1](NATIVE_SOURCE_PORT_PLAN.md#81-why-c-answer-to-the-owners-question) is the natural long-term home.

### Reads that depended on luck: `UNINITIALIZED`, `RETURN-FALLOFF`, `OUT-OF-BOUNDS`, `UNSIZED-ARRAY`

These three kinds of read gave a stable result on the PS1, so the result may matter to gameplay. **Find the old value first**,
then write it down explicitly:

- **Uninitialized:** give it a value at declaration, using what the original's register or stack held when that matters.
- **Falling off the end:** return the value the original left in `$v0`, or make the function `void` if no caller reads it.
- **Out of bounds:** where a read deliberately reached a neighbor, name that neighbor. Use `std::array` or `std::span`
  everywhere else, with bounds checks in Debug.
- **Unsized module arrays:** these are the most urgent of this group. The copy tool gives them one row and loads no bytes,
  so effects read zeros or run past the end. For example, `Effects_Plg049_ringColorFactors` is defined as `[1][4]` while
  `Plg052` reads a sibling table up to 0x1C bytes in. Decode them from the user's disc into a sized `std::span`.

### Pointer width: `POINTER-INT`, `BYTE-OFFSET`, `LITERAL-SIZE`, `PS1-ADDRESS`, `UNPROTOTYPED-CALL`

Use `Handle<T>` or an index when a value is an identity, and named members instead of byte offsets. On-disc bytes go through a
decoder that uses `std::bit_cast`, and never overlay a struct holding pointers. Use `sizeof` or an owning container instead of
literal sizes. [Watchlist section 2](PORTING_WATCHLIST.md#2-64-bit-and-layout-assumptions-handled-during-modernization)
records the earlier fixes in this family, and #172 and #182 show how these fail.

### Room to grow: `CAPACITY`, `CAPACITY-LITERAL`, `NARROW-ID`

Inventory today, from the ledger:

| Category | Capacity | Stored as |
| --- | ---: | --- |
| Weapons | 8 | `Items_InventoryWeapon weapons[8]`, indexed by `u_char` |
| Shields | 8 | `Items_InventoryShield shields[8]`, indexed by `u_char` |
| Blades | 16 | `Items_InventoryBlade blades[16]`, indexed by `u_char` |
| Grips | 16 | `Items_InventoryGrip grips[16]`, indexed by `u_char` |
| Armor | 16 | `Items_InventoryArmor armor[16]`, indexed by `u_char` |
| Gems | 48 | `Items_InventoryGem gems[48]`, indexed by `u_char` |
| Misc items | 64 | `Items_InventoryMisc misc[64]`, indexed by `u_char` |

Raising one of these today means finding every hard-coded loop, every one-byte index, the fixed menu index tables and the
save layout, and missing one corrupts data silently. The `CAPACITY-LITERAL` and `NARROW-ID` rows are that list.

```cpp
// Identity that cannot wrap at 255, and that cannot silently refer to a reused slot.
enum class ItemId : std::uint32_t {};
template <class T> struct Handle { std::uint32_t index; std::uint32_t generation; };

// Storage that follows its own size.
struct Inventory {
  std::vector<BladeInstance> blades;
  std::vector<GemInstance> gems;
};

// The gameplay limit is a policy value. Its defaults keep today's game unchanged.
struct CapacityPolicy {
  std::size_t blades = 16;
  std::size_t gems = 48;
};

// Code follows the container, so raising a limit needs no other edit.
for (auto& blade : inventory.blades) { ... }
```

Suggested order, with each step leaving the game playing the same:

1. Replace `CAPACITY-LITERAL` loops with the array's own size. This changes nothing and removes the hidden copies.
2. Widen `NARROW-ID` fields behind typed IDs. Runtime first, with the save format converting at its boundary.
3. Move storage to `std::vector`, holding it at the policy limit, and drop the PS1-layout `static_assert`s as each type moves.
4. Version the native save format so that a longer list loads correctly and old saves still load. #58 already separates
   definitions from instances and owns this work.
5. Make the menus scroll over any length, and only then raise a limit.

The ledger also lists fixed tables outside inventory that later features may reach, such as `Battle_actors[42]` and
`Actors_actorRecords[17]`.

## Limits

- **Pattern rows can miss sites as well as over-report.** The scanner covers table entries, lookups, and direct reads. It does
  not trace a pointer through function arguments or into another function.
- **Compiler rows** come from one build's warning set and are refreshed with `--compiler-log`. CI cannot re-measure them because
  it does not build, so a new compiler-reported site appears only at the next refresh.
- **Runtime evidence is still missing.** Nothing here shows which sites actually fire. A sanitizer build
  (`-fsanitize=null,bounds`) running the regression suite would show that, and it has not been attempted.
- **The roadmap mapping is proposed,** from each path's system and each issue's title.
