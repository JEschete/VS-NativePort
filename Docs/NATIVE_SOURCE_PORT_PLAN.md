# Vagrant Story: Native Source Port Plan

Status: **Plan v2.** This plan fully replaces v1. v1 put a stand-in PS1 SDK under the decomp code, and that approach is rejected.
Target: Windows x64 desktop, built from one Visual Studio solution at the repo root (`VagrantStory.Native.sln`).

## 0. Decision log

| # | Decision | Choice | Decided by |
|---|---|---|---|
| D1 | What the port is | A **native source port**. Game logic is re-homed into modern C++ systems. There is no emulator, no BIOS, no guest RAM, no MIPS code, and no stand-in PS1 SDK. | Owner |
| D2 | Role of the decomp | `resources\rood-reverseWin` is a **read-only reference**. Nothing in the solution includes, links or loads anything from `resources\`. Code is *copied* into `Native\` once, then owned there. | Owner |
| D3 | Matching | **Not a goal.** No byte matching, no register matching, no keeping the original memory layout. We are free to change types, widen IDs and add content. | Owner |
| D4 | Architecture | **x64 only.** Windows is LLP64 (`long` = 4 bytes), so pointers are the only width change. | Owner |
| D5 | Language | **C++23** for everything in `Native\`. Copied code may land as `.c` (compiled as C17 by clang-cl) for the first compile. It is then **promoted** to `.cpp` per the checklist in §8. End of Phase 2: zero `.c` files. | Owner (agreed) |
| D6 | Layout | Mirrors the DW4 port: root `.sln`, `Native\` with one solution folder per system, versioned JSON schemas, generated assets git-ignored (§3). | Owner (agreed) |
| D7 | Phasing | **Phase 1:** run like the original. **Phase 2:** enhancement. **Phase 3:** go wild. Each has sub-phases (§1). | Owner |
| D8 | SDK replacement | Every PS1 SDK call is retired with one of three strategies: **R** (rewrite at copy time), **T** (temporary translator shim, then migrate and delete), **D** (delete). Each symbol is tracked in the SDK ledger. Shims translate into the *modern* system API and never model hardware (§2.2). | Owner (agreed, "Adjustment B") |
| D9 | Function placement | A function catalog auto-classifies every function to a system. Every function is copied, named, understood and placed, and progress is tracked per function ("Adjustment A"). | Owner (agreed) |
| D10 | Naming speed | The naming/understanding pass is done **up front in Phase 1a**, with parallel subagents per overlay. It is not spread across milestones. | Owner |
| D11 | Data contracts | Def/Instance split, string IDs → runtime handles, versioned schemas validated at load, extract-then-patch layers, data for parameters / code for behaviors, composition for actors (§9). | Owner (agreed) |
| D12 | Dropped references | `psx-spx` and `beetle-psx-libretro` are **not used** and have been removed from `tools\`. We do not consult hardware documentation to build hardware. We consult it only, if ever, to understand what a data format means. | Owner |
| D13 | Compiler | **ClangCL** toolset in `.vcxproj` (accepts the GCC extensions in copied C, `/std:c++latest`). MSVC `cl` stays allowed for pure C++ projects. | Proposed |
| D14 | Renderer backend | **SDL3 GPU** (D3D12/Vulkan/Metal underneath; shaders in HLSL via SDL_shadercross) behind our own `VS.Render` API. A direct D3D12 backend can be added later behind the same API if Phase 3 needs ray tracing, mesh shaders or bindless. | Owner (2026-10-15) |
| D15 | Third-party | SDL3 (zlib), vendored. CC0/MIT code may be lifted with attribution (rood-boi device logic, PsyCross GTE math). GPL / non-commercial / unlicensed code is reference only. | Proposed |
| D16 | Upstream contributions | Renames are **not** sent back to rood-reverse | Owner |
| D17 | Enemy data | Species / EnemyDef (`extends` variants) / Loot / Spawn catalogs, with behaviors in code. See [ENEMY_DATA_SCHEME.md](ENEMY_DATA_SCHEME.md) | Owner asked to modernize; design v1 |
| D18 | Asset pipeline | `VS.Extract` converts **every** disc file **up front** into `Native\data\` (git-ignored). The game never reads the disc. See [ASSET_PIPELINE.md](ASSET_PIPELINE.md) | Owner (2026-10-15) |
| D19 | Build instructions | [BUILDING.md](BUILDING.md) is the single source of truth for clone → build → extract → play. Every change to prerequisites, scripts, dependencies, output layout or extraction updates it **in the same commit**. Planned steps are marked ⏭ until they land. | Owner (2026-10-15) |

### 0.1 What "not an emulator" means, concretely

| Forbidden in `Native\` | Replaced by |
|---|---|
| A byte array representing PS1 RAM, scratchpad, VRAM or SPU RAM | Typed C++ objects owned by each system |
| Addresses such as `0x80xxxxxx`, `0x1F80xxxx` or KSEG literals | Pointers, references, handles |
| Ordering tables, GPU packets, `DR_*` primitives as the render API | `RenderQueue` with sort keys and typed draw items |
| GTE registers or `gte_*` macros | `VS::Math` fixed-point vectors/matrices (bit-accurate where gameplay depends on it) |
| SPU voices addressed by register, SPU RAM transfers | `VS::Audio` voices, banks, mixer |
| CD sectors, LBAs, `CdlLOC`, `DsRead` callbacks | `VS::Content` file IDs, async loader, decoded assets |
| `VSync()` / vblank callbacks / root counters | `VS::Core::FrameClock` fixed-step tick (Phase 1: 60 Hz field timing reproduced) |
| Overlay loading of `*.PRG` files | Statically linked modules with explicit `Init/Reset/Update` |
| `StoreImage` / `MoveImage` readback of "VRAM" | `VS.Render` render-target capture API (§6.2) |

## 2. Hard rules

### 2.1 Code rules

1. **No `#include` into `resources\`.** A CI check greps every `.vcxproj` and source file for `resources` and `rood-reverse`.
2. **No guest addresses.** A CI check (`tools\lint\native_boundary.py`) fails on the patterns `0x80[0-9A-F]{6}`, `0x1F80`, `0xA0[0-9A-F]{6}`, `getScratchAddr` and `D_80` in `Native\`. A narrow allow-list is used for provenance comments only.
3. **Provenance comments.** Every copied function carries one line:
   `// decomp: BATTLE.PRG func_8006B57C (src/BATTLE/BATTLE.PRG/…c:123)`.
   The ledger links back the same way. This replaces any need to keep original names in code.
4. **No raw struct I/O.** Nothing is `fread` into a struct. Every disc format has a decoder that produces typed objects (§6.5).
5. **System ownership.** A system's state lives in that system. Cross-system calls go through its public header (`Native\<System>\include\vs\<system>\…`).
6. **Warnings are errors** for promoted `.cpp` files. Copied `.c` gets a relaxed warning set that is tracked and tightened on promotion.

### 2.2 Transitional shims (strategy T)

Shims exist only to make a large body of copied code compile and run *before* every call site is rewritten. Rules:

- They live only in `Native\<System>\Legacy\` and are named after the SDK function (e.g. `Legacy\gpu_prims.cpp` provides `AddPrim`, `SetPolyFT4`).
- They **translate** into the modern system API. For example, `AddPrim(ot, polyFT4)` becomes `RenderQueue::Submit(SortKey{layer, z}, TexturedQuad{…})`. They never keep a hardware model (no VRAM array, no OT walk at draw time, no SPU RAM).
- Each shim symbol has a row in `SDK_API_LEDGER.md` with its live use count. When the count hits 0, the shim is deleted and the row goes `[x]`.
- New code may never call a shim. A CI check counts shim uses, and the count may only go down.

## 4. Ledgers: the source of truth

The owner requirement is a VERY detailed list of what is done and not done. The ledgers are that list. They are **generated from the decomp** (so nothing is missed) and **hand/agent-filled** for status (preserved on regeneration).

### 4.1 FUNCTION_CATALOG.csv (master list)

One row per game function: **3,679 rows**. There are 2,918 C functions, 480 effect template instantiations, 191 asm-only, 37 in headers, 28 template bodies and 25 `INCLUDE_ASM`. 2,231 still have generic names. 442 SDK library functions are excluded because they are replaced, not copied.

| Column | Meaning |
|---|---|
| `id` | Stable row ID |
| `overlay`, `unit`, `file`, `line` | Where it lives in the decomp |
| `name`, `kind`, `generic` | Decomp name, row kind, still `func_`? |
| `lines`, `callers`, `callees` | Size and call graph (for ordering work) |
| `proposed_system`, `basis` | Auto-classification and why (api / name / unit / unit-low / none) |
| `copy` | `yes` / `template` (becomes data + shared code) / `asm` (rewrite from asm + Ghidra) |
| `sdk_apis` | SDK symbols it calls (links to the SDK ledger) |
| `hw_reg … inline_asm` | Hazard counts (scratchpad, KSEG literals, 24-bit OT, pointer casts, inline asm) |
| `final_name` | Native C++ name (`Namespace::Function` or `Class::Method`) |
| `final_location` | `Native\…\File.cpp` |
| `purpose` | One-sentence description of what it does |
| `copied` … `verified` | Status (below) |
| `notes` | Free text |

**Status lifecycle (definition of done per column):**

| Column | `yes` means |
|---|---|
| `copied` | The function body exists at `final_location` with a provenance comment |
| `compiles` | It builds in Debug and Release x64 with zero errors |
| `named` | `final_name` is set and used in code, all parameters and locals have meaningful names, no `argN`/`varN`/`unk` remain |
| `understood` | `purpose` is filled, and every struct field it touches is named in the type ledger |
| `modernized` | It has no SDK shim calls, no hazards, no globals owned by another system, and uses typed data |
| `cpp` | It lives in a `.cpp` file that passes the promotion checklist (§8.2) |
| `verified` | It is covered by a test, a replay hash or a capture comparison |

### 4.3 SOURCE_FILE_LEDGER.md

There are 440 decomp files (261 game, 179 SDK), each with checkboxes **C**opied / **B**uilds / **N**amed / **M**odernized / **P**romoted / **V**erified, plus hazard totals and the systems its functions go to. Use it to drive file-by-file work.

### 4.4 DATA_LEDGER.csv

Generated by `tools\ledger\build_symbol_ledgers.py` from `build\port\data.json`. There is one row (`G#####`) per
**storage identity**, not per spelling: a file `static`, a function-local `static`, an overlay's `D_` extern and a
shared-header table instantiated in several overlays are all separate pieces of storage, even when they share a name.
That gives 2,174 identities from 1,751 spellings (916 still generic). Each row carries the generator's
`proposed_disposition` and `proposed_system` (the majority system of its referencing functions); the naming pass fills
`disposition`, `final_name`, `final_location`, `purpose` and `confidence` ([NAMING_CONVENTIONS.md](NAMING_CONVENTIONS.md) §8).
Each row gets a `disposition`:

| Disposition | Meaning |
|---|---|
| `catalog` | It is game content (item stats, enemy tables, text, effect params). VS.Extract converts it from the user's disc into a schema'd JSON catalog in `Native\data\catalogs\`, using a decoder generated from the decomp struct ([ASSET_PIPELINE.md](ASSET_PIPELINE.md) §4). It is **never committed**. |
| `constexpr` | It is engine constants (lookup tables, sin tables, layout constants). It is re-expressed as `constexpr` in code, either computed or proven equal by a test against the disc bytes. |
| `state` | It is runtime mutable state, and it becomes a member of the owning system's state struct. |
| `asset` | It is a reference to graphics/audio, and it becomes an `AssetId`/handle into `Native\data\`. |
| `drop` | It is hardware buffers, OTs, packet pools and anything else that has no meaning natively. |

### 4.6 Coverage facts (verified)

- The disc has 331 code files (`*.PRG`, `PLG*.BIN`, `EFFPURGE.BIN`). Of these:
  - **91** have decomp source.
  - **48** are byte-identical copies of a covered plugin.
  - **192** are **zero-byte placeholders** (including `MENUA.PRG`).
- **Therefore 100 % of the shipped game code is covered by the decomp.** No code needs to be written from disassembly alone, except the 191 asm-only + 25 `INCLUDE_ASM` functions, which have asm and Ghidra available.

## 5. Phase 1a workflow (in order)

### Step 1: Baseline ledgers (**done**)
Run `python tools\ledger\build_ledgers.py`. Commit the output.

### Step 2: Solution skeleton
Create `VagrantStory.Native.sln`, `Directory.Build.props`, and empty projects per §3. Vendor SDL3. `VS.Desktop` opens a window and pumps input. Add the CI scripts (`build-native.cmd`, `test-native.cmd`, boundary lint).

### Step 3: Naming & understanding pass (parallel subagents)

- **Work units:** one batch per overlay/source file, sized to about 150–250 functions. BATTLE.PRG (1,850 rows) is split by source file and call-graph clusters.
- **Inputs per agent:**
  - the decomp source (read-only);
  - callers/callees from the catalog;
  - the DataCrystal pages (`resources\DataCrystal`), GodHands (`tools\PSX\VagrantStory\GodHands`), vstrack, and the Unity VS parser;
  - Ghidra (MCP) for asm-only functions.
- **Outputs per row:** `final_name`, `purpose`, `final_location`, struct-field names discovered, and confidence (high/med/low → `notes`).
- **Conflict resolution:** a single merge script applies agent outputs to the CSV. Duplicate `final_name`s and low-confidence rows are re-queued.
- **Order:**
  1. SLUS (shared engine) first, so that its names feed every overlay.
  2. TITLE, MAINMENU, MENU*.
  3. BATTLE.
  4. EFFECT.
  5. ENDING and the rest.
- **Gate:** every row has `final_name` + `final_location` + `purpose`; `Triage` = 0.

### Step 4: Copy tool (`tools\port\copy_to_native.py`)
For each row (in file order):

1. Extract the function body from the decomp.
2. Rename the symbol and all known callees/globals using `final_name`s and the data/type ledgers.
3. Apply **R rewrites**:

   | From | To |
   |---|---|
   | `gte_*` / `RotTransPers` … | `VS::Math` calls |
   | `PadRead` … | `VS::Input::Pad` |
   | `memcpy`/`memset`/`strcpy` | `std::` |
   | `rand` | `VS::Core::Random` |
   | `VSync` | `FrameClock` |
   | `getScratchAddr(n)` | a member of the module's scratch-state struct |

4. Delete **D** calls (critical sections, `DrawSync`, `SetDispMask`, `ResetGraph`, `InitGeom`, debug font, SPU IRQ/transfer setup, …).
5. Leave **T** calls, which resolve to `Legacy\` shims.
6. Write the result to `final_location` with a provenance comment, and generate the module headers.
7. Mark `copied`.
8. Effect template instantiations (`copy = template`) are **not** duplicated. One shared implementation per template (`tiledRings`, `particleSetup`, `trails9`, …) is copied. Each instantiation becomes a row in the effects catalog (§6.8).

### Step 5: Data disposition and asset extraction
Fill in `disposition` in the data ledger and generate the Tier 1 table decoders for `catalog` rows. Convert `constexpr` rows. Fold `state` rows into system state structs. Build the `VS.Extract` skeleton and manifest, generate `CONTENT_LEDGER.csv`, and write the converters in the order the 1b title slice needs them. Every disc file is converted up front by Phase 1 exit; the per-sub-phase asset gates are in [ASSET_PIPELINE.md](ASSET_PIPELINE.md) §9.

### Step 6: Compile everything
Fix until the solution builds. Hazards are fixed now, not later (x64):

| Hazard | Fix |
|---|---|
| pointer casts | proper types |
| 24-bit OT links | sort keys |
| KSEG literals | handles |
| inline asm | C++ |

Mark `compiles`.

### Step 7: Gate review
Confirm that the ledger percentages match §1, that the CI lint is clean and that the tests are green.

## 6. Per-system designs

Each system lists: responsibility, API sketch, ledger rows it absorbs, Phase 1 work, Phase 2+ work and tests.

### 6.1 Core (`VS.Core`)
- **Responsibility:** fixed-point math, random, timing, logging, assertions, memory arenas, typed handles.
- **API:**
  - `Fixed12` (4.12) and `Fixed16`;
  - `Vec3s`, `Vec3i`, `Mat3x3s`, `Transform`;
  - `RotTrans`, `RotTransPers`, `NormalClip`, `AverageZ`, `Project`, with explicit rounding that matches the original where gameplay depends on it;
  - `Random` (reproduces the original `rand` LCG sequence for replay parity);
  - `FrameClock` (logical ticks; the original's field-based 60/30/20 fps steps).
- **Absorbs:** libgte (41 symbols, 1,489 uses), libc/crt, libetc VSync, `Core.Math` (41 rows), `Core` (44 rows).
- **Tests:** a math oracle against the PsyCross GTE and ps1-tests GTE vectors; LCG sequence; transform round-trips.

### 6.2 Graphics (`VS.Render`)
- **Responsibility:** everything visible. The game submits *what* to draw, and the backend decides *how*.
- **Model:**
  - `RenderQueue` per frame. Draw items carry a `SortKey { layer, depth, sequence }`, which replaces OT index + `AddPrim` order. Reverse-depth ordering is reproduced by the key, not by a linked list.
  - Draw items: `Triangle/Quad` (flat, gouraud, textured, textured-gouraud), `Sprite`, `Tile`, `Line`, `Fill`.
  - Materials: `BlendMode { Opaque, Half, Add, Sub, AddQuarter }`, `TextureRef`, `Palette`, semi-transparency flags.
  - **Texture page space:** the original data refers to textures by tpage/clut coordinates. `VS.Render` keeps a *logical* 1024×512 texture-page space that maps those coordinates to real GPU textures and palettes. It is a lookup structure (rect → texture + palette), not emulated VRAM. TIM uploads (`LoadImage`) register textures in that space.
  - **Capture API:** `Capture(rect) → TextureHandle` replaces `StoreImage`/`MoveImage` readbacks (title menu background, screen effects, battle transitions).
  - Display: `SetDisplayArea`, `SetClearColor`, fades, letterbox, all as typed calls.
- **Absorbs:** libgpu (78 symbols, 1,742 uses) via `Legacy\gpu_*.cpp` shims, then migrated; `Graphics` (121 rows).
- **Phase 1:** native resolution 320×240 (and the 512/640 modes the game uses), point sampling, affine mapping, dithering optional. Parity first.
- **Phase 2:** resolution scale, widescreen, perspective-correct mapping, sub-pixel vertices, 60 fps interpolation (the queue stores previous transforms).
- **Tests:** capture comparison of title, menu and first room against DuckStation reference images with a tolerance metric.

### 6.3 Audio (`VS.Audio`, `VS.Audio.Sequencer`)
- **Responsibility:** music, SFX, voice/XA streams.
- **Model:**
  - `SampleBank` holds 16-bit PCM loaded from `Native\data\audio\samples\*.wav` (ADPCM was decoded by VS.Extract) and its instrument data from `audio\banks\*.json`.
  - `Voice` holds pitch, ADSR envelope and volume/pan, emulated *behaviorally* at the envelope level, not at the register level.
  - `Mixer` runs at 48 kHz with float mixing.
  - `Reverb` presets are equivalent to the original modes.
  - `StreamPlayer` plays the FLAC streams converted from XA.
- **Sequencer:** the decomp's AKAO sequence interpreter (in `Audio`, 254 rows) is copied and becomes `VS.Audio.Sequencer`. It drives `Voice`s directly instead of SPU registers, and it reads the decoded `*.seq.json` event lists (music stays sequenced, D18).
- **Absorbs:** libspu (36), libsnd (2) via `Legacy\spu_*.cpp` → migrated.
- **Phase 2:** better resampling, optional interpolation modes, volume channels, replacement music hooks.
- **Tests:** sequence-event traces versus a reference capture; ADPCM decoder versus known vectors.

### 6.4 Video (`VS.Movie`)
- **Responsibility:** FMV playback (the movies in `TITLE.STR`, converted to `Native\data\movies\*.mkv`).
- **Model:** libwebm demuxes the Matroska file, dav1d decodes AV1 to YUV planes that a shader converts on an SDL3 GPU texture, and the FLAC audio goes through `VS.Audio.StreamPlayer`. Presentation is clocked to the audio. VS.Extract does the STR → AV1 conversion up front with ffmpeg (extract time only; [ASSET_PIPELINE.md](ASSET_PIPELINE.md) §6.7).
- **Absorbs:** libpress (13 symbols) via shim → migrated; `Video` (15 rows); the title movie functions (`_initIntroMovie`, `_playIntroMovie`).
- **Reuse:** none at runtime. jpsxdec decodes are the reference used to validate the conversion.
- **Tests:** PSNR ≥ 45 dB of decoded MKV frames against a jpsxdec decode; frame count and duration equal.

### 6.5 Input (`VS.Input`)
- **Responsibility:** devices → actions.
- **Model:**
  - `Action` enum (Confirm, Cancel, Menu, Camera…).
  - A `PadState` with the original PS button bitmask for Phase 1 parity (the game logic reads it).
  - SDL3 gamepad and keyboard bindings.
  - Rumble (the title's Vibration option) maps to SDL rumble.
- **Absorbs:** libpad (25 symbols, 544 uses), rewritten at copy time (R); `Input` (17 rows).
- **Phase 2:** remapping UI, per-device prompts.
- **Tests:** binding resolution; pad edge detection (pressed/held/repeat) matching the original repeat timings.

### 6.6 Content (`VS.Content`)
- **Responsibility:** the disc (for VS.Extract only), every format on it, and loading the converted content in `Native\data\` (D18).
- **Model:**
  - `Disc` opens `.bin/.cue` (mode 2 raw sectors) and parses ISO9660 itself. **Only VS.Extract uses it**; the game never reads the disc.
  - `AssetId` registry: every file the game references by LBA or index becomes a named ID (`asset.movie.title`), mapped to its converted file(s) in `Native\data\`.
  - `AsyncLoader` does background loads with completion handles, replacing `DsRead` callbacks.
  - **Decoders** (used by VS.Extract and the round-trip tests) produce typed objects: TIM, MPD, ZND, SHP, SEQ, WEP, ARM, ZUD, SYD, FBT/FBC, EVT, AKAO, XA, MCDATA, ITEMNAME/ITEMHELP text, HF0/HF1 help, EFFECT data.
  - **Loaders** (used by the game) read glTF, PNG, WAV, FLAC and JSON from `Native\data\` and build the same typed objects. The round-trip rule in ASSET_PIPELINE §7 proves `decode(raw) == load(converted)`.
  - **Catalogs** are loaded from `Native\data\catalogs\` JSON, validated against `schemas\`, and frozen into immutable registries (§9).
- **Absorbs:** libds (33), libcd (1) via shim → migrated; `Content` (56 rows).
- **Tests:** a decoder round-trip for every format against the GodHands / Unity-parser interpretations; the converter round-trips (ASSET_PIPELINE §7); catalog round-trip (§9.8).

### 6.7 Save (`VS.Save`)
- **Model:** a versioned JSON (or binary + schema) save with string IDs for every item/location, plus an import of PS1 `.mcd`/`.mcr` saves via a decoder.
- **Absorbs:** libcard (4), libapi card events, `Save` (68 rows).
- **Tests:** save → load round-trip; import of a known PS1 save gives the expected inventory.

### 6.8 Game modules (`VS.Game`)

| Module | Origin | Notes |
|---|---|---|
| `Boot` | SLUS `main` boot path | Builds systems and runs the top-level state machine **Boot → Title → Game ⇄ Battle/Menu → Ending**, replacing `jumpToTitle`/`jumpToBattle`/overlay swaps. |
| `Title` | TITLE.PRG (98 functions, all named) | Dev credits, intro movie, title menu, attract loop. **1b target.** |
| `Field` | SLUS + BATTLE field parts | Room/zone loading, camera, collision, doors. |
| `Battle` | BATTLE.PRG (1,850 functions) | Combat, risk, chains, AI. Largest naming job. |
| `Actors` | SLUS/BATTLE | Composition: `Transform`, `Model`, `Animator`, `Stats`, `Equipment`, `AI`, `Collider` components. |
| `Items` | BATTLE/MENU | Inventory, equipment, workshops, combine. Uses Defs from catalogs + Instances (§9). |
| `Menu` | MAINMENU + MENU0–F | Each MENUx becomes a screen class registered with a menu stack. |

Overlays become modules with explicit `Init()`, `Shutdown()`, `Update(dt)` and `Reset()`. Statics that the original re-initialized by reloading the overlay are reset in `Reset()`.

## 7. Retirement strategies, in detail

| Strategy | When | Mechanism | Tracking |
|---|---|---|---|
| **R: rewrite at copy** | The replacement is mechanical and 1:1 (math, pad reads, crt, rand, VSync, scratchpad) | The copy tool rewrites call sites into the modern API | The SDK row goes straight to `[x]` once the copy is done |
| **T: temporary shim** | The replacement needs design work at each call site (draw primitives, SPU, Ds, Press, Card) | A `Legacy\` function with the SDK name that translates into the modern API | `[ ]` → `[A]` shim exists → `[M]` all call sites migrated → `[x]` deleted |
| **D: delete** | No native meaning (critical sections, events, DrawSync, SetDispMask, ResetGraph, InitGeom, debug font, SPU IRQ setup, Ds ready system) | The copy tool removes the call, and any needed effect is reproduced by the system | `[x]` at copy |

Ordering of T migrations follows the milestones. Title shims (gpu sprites, StoreImage, press, ds) are migrated in 1b, field/battle in 1c, and the rest by 2e.

## 8. C vs C++

### 8.1 Why C++ (answer to the owner's question)

The decomp stays as a reference in C, so the port gains nothing from staying in C. C++23 gives:

| Benefit | Detail |
|---|---|
| Type safety for IDs | `enum class`, `Handle<T>`, `ItemId` instead of `u_char`, which also removes the 255 cap |
| Value types with operators | `Fixed12`, `Vec3`, `Mat3` (the GTE replacement reads like math) |
| RAII | Textures, files, voices and loaders clean themselves up, with no leak paths through module resets |
| Real containers | `std::vector`, `std::span`, `std::array`, flat maps, instead of fixed arrays plus counters |
| Compile-time checks | `constexpr` tables, `static_assert` on formats, `consteval` validation of constant data |
| Namespaces/classes | Map 1:1 onto systems and modules, with no `vs_battle_` prefixes |
| Variants/visitors | Draw items, effect kinds, event commands |
| Exceptions-free error handling | `std::expected` for decoders and loaders |
| Testability | Systems are objects that can be built in isolation |

Costs: compile times (mitigated by PCH and static libs), and the temptation to over-abstract (mitigated by "data for parameters, code for behaviors").

### 8.2 Promotion checklist (`.c` → `.cpp`, sets `cpp = yes`)
1. Rename the file, and fix C-only constructs (implicit `void*` casts, designated-initializer order, `restrict`, VLAs).
2. Move it into `namespace VS::<System>`. Free functions become methods where they operate on one state object.
3. Replace raw IDs with typed IDs/handles, and fixed arrays with `std::array`/`std::span`.
4. No remaining shim calls (`modernized = yes` is a prerequisite).
5. Full warning set (`-Wall -Wextra`, warnings as errors) is clean.
6. Covered by a test or a replay hash (`verified` is ideally already yes).

## 9. Data contracts & patterns

### 9.1 Def vs Instance (Type Object pattern)
The original mixes the two. For example, `vs_main_inventoryBlade` stores `u_char id` plus the mutable DP/PP and bitfields in one struct. We split them:

```cpp
struct BladeDef {                 // immutable, from catalog
    ItemId id;                    // "blade.scramasax"
    TextId name, help;
    BladeCategory category;       // Dagger, Sword, ...
    DamageType damageType;        // Blunt, Edged, Piercing
    Material defaultMaterial;
    int16_t str, intel, agl;
    int16_t range, risk;
    uint16_t maxDp, maxPp;
    std::vector<GripCategory> compatibleGrips;
    ModelRef model;
};

struct BladeInstance {            // mutable, lives in GameState / save
    Handle<BladeDef> def;
    Material material;
    uint16_t dp, pp;
    ClassAffinities classAffinity;   // human, beast, undead, ...
    ElementAffinities elementAffinity;
};
```

### 9.2 String IDs → runtime handles
- Catalogs and saves use **stable string IDs** (`"blade.scramasax"`, `"enemy.minotaur"`, `"room.wine_cellar.entrance"`).
- At load, a `Registry<T>` interns them into dense `Handle<T>` (a `uint32_t` index) for O(1) lookup. Code uses handles, and data and saves use strings.
- Phase 1 also records the **original numeric ID** (`legacyId`) on every Def, so that copied logic and `.mcd` import still work.

### 9.3 Catalogs (one schema each, `Native\Content\schemas\`)

| Catalog | Source on disc (to verify per CONTENT_LEDGER) |
|---|---|
| `blades`, `grips`, `gems`, `armor`, `shields`, `accessories` | `MENU\BLADE.SYD`, `ARMOR.SYD`, `SHIELD.SYD`, `SMALL\*.DIS/*.ARM`, SLUS tables |
| `consumables`, `materials`, `misc-items` | SLUS/BATTLE tables |
| `item-text` | `MENU\ITEMNAME.BIN`, `ITEMHELP.BIN`, `SMALL\HELP*.HF0/HF1` |
| `species`, `enemies` (base + `extends` variants), `modelsets`, `bestiary` | ZND enemy sections (455 records in 49 zones), ZUD archives, `MON.BIN`. See [ENEMY_DATA_SCHEME.md](ENEMY_DATA_SCHEME.md) |
| `loot` (shared drop tables) | Per-slot drop rates lifted out of the ZND records |
| `break-arts`, `battle-abilities` (chain/defense), `spells`, `status-effects` | BATTLE tables |
| `workshops`, `combine-tables` | MENU tables (blade/armor combination matrices) |
| `rooms` (incl. `spawns[]` with conditions), `zones`, `doors`, `keys`, `chests`, `save-points` | MPD/ZND + SLUS tables |
| `text` (dialog, UI) | event data, MCDATA, menu text |
| `music`, `sfx` | sound bank/sequence index tables |
| `effects` | EFFECT plugin parameters (480 template instantiations) |
| `events` | event script data |
| `title` | title-screen layout, timings (1000/100 tick timeouts), menu items |

### 9.4 Schema rules (from DW4 `schemas\README.md`)
- Every file has `"schema_version"`. Loaders accept known versions only, and migrate forward (never downgrade).
- Validation at load: types, ranges, references (every `ItemId` resolves), uniqueness. Errors name the file, the JSON pointer and the rule.
- After validation, data becomes **immutable** typed records (frozen registries).
- Converted payloads (`Native\data\`) are git-ignored. Only the schemas, the extractor and the patches are committed. See [ASSET_PIPELINE.md](ASSET_PIPELINE.md).

### 9.5 Example catalog entry

```json
  "blades": [
    {
      "id": "blade.scramasax",
      "legacyId": 2,
      "name": "text.item.blade.scramasax.name",
      "category": "dagger",
      "damageType": "piercing",

```

### 9.6 Patch layers (mods)
Load order: `Native\data\` (converted from the disc) → `Native\Content\patches\` (our fixes/enhancements) → `mods\<name>\` (user). Mods may also replace converted assets (glTF, PNG, WAV, sequences, movies) by path.
Patch operations: `add`, `replace`, `merge` (field-level), `remove`, by ID. A conflict report lists every ID that more than one layer touched.

### 9.7 Behaviors stay in code
Catalogs hold **parameters**. **Behaviors** (AI routines, effect kinds, event commands, break-art scripts) are C++ registered by name in a `BehaviorRegistry`. Data refers to behaviors by name (`"ai": "ai.minotaur"`). New behaviors are added in code in Phase 3a, or in the script layer in 3b.

### 9.8 Phase 1 parity rule
Phase 1 catalogs must reproduce the original **exactly**. A round-trip test decodes the disc table, serializes it to the catalog, loads the catalog and compares field-for-field with the original values. Enhancements go into patch layers, never into the base catalog.

### 9.9 Determinism
Fixed-step simulation, the original RNG sequence, no wall-clock in game logic, and no unordered-container iteration in gameplay. This enables replays (`--replay file`) and state hashes for verification.

## 12. Risks

| Risk | Mitigation |
|---|---|
| BATTLE naming quality (1,478 generic) | Parallel agents with call-graph context, confidence tags, re-queue of low-confidence rows, and name review at the 1c gate |
| Hidden layout dependence (pointer arithmetic on structs, 24-bit OT tricks, 278 pointer casts) | Fixed at compile time in 1a; type ledger; asserts in decoders, not on runtime structs |
| Scratchpad use (1,034 hits) | Becomes per-module scratch structs; tracked as a hazard until 0 |
| Readback-dependent effects (`StoreImage`/`MoveImage`) | Capture API in VS.Render from 1b |
| Timing parity (30/20 fps logic, field timing) | FrameClock reproduces logical ticks; replays catch drift |
| Effects volume (480 instantiations, ~90 plugins) | Template + catalog design; previewer in 2d |
| Asm-only functions (191 + 25) | Rewritten from asm + Ghidra; marked in the catalog `copy = asm` |
| Enemy variants diverge in ways `extends` cannot express cleanly | The round-trip test (ENEMY_DATA_SCHEME §3) catches it; worst case, a variant is emitted in full |
