# Vagrant Story: Native Source Port Plan

Status: **Plan v3: implementation and retirement roadmap.** The native-system destination from v2 remains the
target; existing compatibility implementations are documented rather than counted as already modernized.
Target: Windows x64 desktop, built from one Visual Studio solution at the repo root (`VagrantStory.Native.sln`).

**How to use this plan:** §0 and §6 define the destination; §0.2 records the inspected baseline; §14 defines the
executable work packages and acceptance gates. §5 and §13.1 retain historical foundation work, not current proof
that a subsystem runs correctly. No new runtime verification or owner approval is implied by this document update.

### 0.1 Target meaning of "not an emulator"

The decision log records the intended end state, not a claim that today's runtime meets every rule. The current
page-image renderer, SPU memory/register blocks and original-address adapters are deviations described in the audit.
Preserve the existing retirement goal unless an explicit decision changes it; §13.3 lists the unresolved choices.

| Excluded from the target shipping runtime | Replaced by |
|---|---|
| A byte array representing PS1 RAM, scratchpad, VRAM or SPU RAM | Typed C++ objects owned by each system |
| Addresses such as `0x80xxxxxx`, `0x1F80xxxx` or KSEG literals | Pointers, references, handles |
| Ordering tables, GPU packets, `DR_*` primitives as the render API | `RenderQueue` with sort keys and typed draw items |
| GTE registers or `gte_*` macros | `VS::Math` fixed-point vectors/matrices (bit-accurate where gameplay depends on it) |
| SPU voices addressed by register, SPU RAM transfers | `VS::Audio` voices, banks, mixer |
| CD sectors, LBAs, `CdlLOC`, `DsRead` callbacks | `VS::Content` file IDs, async loader, decoded assets |
| `VSync()` / vblank callbacks / root counters | `VS::Core::FrameClock` fixed-step tick (Phase 1: 60 Hz field timing reproduced) |
| Overlay loading of `*.PRG` files | Statically linked modules with explicit `Init/Reset/Update` |
| `StoreImage` / `MoveImage` readback of "VRAM" | `Engine\Render` render-target capture API (§6.2) |

### 0.2 Inspected baseline and two progress tracks

Baseline: HEAD `680baf18` plus local sources inspected while writing the compatibility audit. This is a source
snapshot, not a fresh build/test result. Refresh it when closing a package; do not copy old log results into a new gate.

| Area | Implemented foundation | Still not established by that foundation |
|---|---|---|
| Execution/platform | Native `Boot_RunGame` on a Windows fiber; SDL event loop and crash diagnostics | Explicit module lifecycle, full title/gameplay parity |
| Graphics | GP0/ordering-table compatibility renderer and SDL GPU image presentation | Typed native draw queue, native geometry/material path |
| Input/verification | Native pad state, legacy receive-buffer adapter, `--press`/`--scripted`, bounded captures | Complete recording/replay, canonical state comparison, input-adapter retirement |
| Content | Extracted regular files, LBA manifest, module data/pointer initialization | Fully validated relocations, typed/versioned assets, disc-independent startup |
| Audio | SDL output/source-stream infrastructure, copied sequencer, SPU-shaped transfers/registers | Verified sequencer-to-audible-output path and register-free voice API |
| Movie/save | Movie-player interface and intro timing path; basic save-slot helpers | Movie decoding and A/V parity; versioned, recoverable save/load |

Track **behavior** (`implemented → integrated → reference-verified`) separately from **architecture**
(`copied → compatibility-backed → native API → legacy dependency retired`). A compatibility-backed screen can
be verified without being modernized. A new API or `.cpp` file can be modern-looking without verified behavior.
Original RNG, fixed-point rules, event scripts and AKAO sequencing are game semantics, not automatically emulation.

## 2. Hard rules

### 2.1 Code rules

1. **No `#include` into `resources\`.** A CI check greps every `.vcxproj` and source file for `resources` and `rood-reverse`.
2. **No guest addresses in modernized runtime code.** Boundary lint checks address/scratchpad patterns including
   `0x80[0-9A-F]{6}`, `0x1F80`, `0xA0[0-9A-F]{6}`, `getScratchAddr` and `D_80`. M0 must distinguish provenance,
   extraction-only source metadata, non-address constants and the exact existing compatibility exceptions. Each
   runtime exception needs an EC issue and retirement package; do not disable the check for an entire project.
3. **Provenance comments.** Every copied function carries one line:
   `// decomp: BATTLE.PRG func_8006B57C (src/BATTLE/BATTLE.PRG/…c:123)`.
   The ledger links back the same way. This replaces any need to keep original names in code.
4. **No raw struct I/O in the target runtime.** Every disc format has an explicit decoder that produces typed
   objects (§6.6). The existing module-image copies are EC-04 bridge work, not compliance with this rule. Original
   layout offsets may be used by extraction decoders, never assumed equal to native pointer-bearing layouts.
5. **System ownership.** A system's state lives in that system. Cross-system calls go through its public header (`Native\Engine\include\<System>\…`, `Native\Game\include\<Module>\…`, `Native\Content\include\Content\…`). Inside one project this is enforced by lint, not by project references.
6. **Warnings are errors** for promoted `.cpp` files. Copied `.c` gets a relaxed warning set that is tracked and tightened on promotion.

### 2.2 Transitional shims (strategy T)

Shims exist to make copied code run *before* every call site is rewritten. The rules below describe the desired
boundary; the audit records existing departures, including hardware-shaped helpers outside `Legacy`. Recording
a departure does not approve its permanent retention. M0 establishes the exact inventory and enforcement baseline.

- They live only in `Native\Engine\Legacy\<System>\` (or `Native\Content\Legacy\`) and are named after the SDK function (e.g. `Legacy\gpu_prims.cpp` provides `AddPrim`, `SetPolyFT4`).
- They **translate** into the modern system API. For example, `AddPrim(ot, polyFT4)` becomes `RenderQueue::Submit(SortKey{layer, z}, TexturedQuad{…})`. They never keep a hardware model (no VRAM array, no OT walk at draw time, no SPU RAM).
- Each shim symbol has a row in `SDK_API_LEDGER.md` with its live use count. When the count hits 0, the shim is deleted and the row goes `[x]`.
- New code may never call a shim. A CI check counts shim uses, and the count may only go down.

New native gameplay code uses the public system API. Bridge repairs needed to unblock a verified slice must identify
their EC issue, affected consumers, tests and removal package. Any temporary increase requires explicit review;
it must not be hidden by renaming SDK calls. Missing behavior is classified as required or optional per checkpoint:
required data/dispatch failure stops before use, while an optional omission is reported and cannot pass its feature gate.

## 3. Solution layout

Owner decision 2026-10-17 (**hybrid**): DW4's few-projects style (`D:\Dev\NativePort\DW4_NativePort2`), with the
engine systems grouped in one project. `tools\scaffold\gen_solution.py` generates the solution, every `.vcxproj`
and its `.vcxproj.filters` from one table. Files are listed explicitly and every folder on disk is a filter, so
Solution Explorer mirrors the tree. Re-run the generator after adding or removing files (the copy tool does).

```
VS-NativePort\
  VagrantStory.Native.sln            ← open this, F5 runs VS.Desktop
  Directory.Build.props              ← x64, C++23 / C17, ClangCL (needed for the decomp's GNU C), warnings, output dirs
  build-native.cmd  test-native.cmd  extract-native-assets.cmd  package-native.cmd
  vcpkg.json                         ← manifest: SDL3, Catch2, nlohmann-json (+ dav1d, libwebm, libflac, lodepng as converters land)
  Native\
    Engine\         VS.Engine        engine systems, one folder each under src\, include\ and Legacy\:
                      Core\       types, Fixed/Vec/Mat (GTE replacement), Random, FrameClock, Log, Assert, Arena, Handle<T>
                      Platform\   SDL3 window, file system, timers, paths, crash handler
                      Render\     RenderQueue, sort keys, materials/blend modes, texture page space, capture/readback, SDL3 GPU backend
                      Audio\      sample banks, voices, mixer, reverb, stream player; Audio\Seq is the AKAO sequencer
                      Input\      actions, PS button map for parity, SDL3 gamepad, keyboard, rumble
                      Movie\      Matroska demux (libwebm) + AV1 decode (dav1d) → texture, audio sync
                      Save\       versioned save format, .mcd import
                    Legacy\<System>\  T-shims (libgpu, libspu/libsnd, libpress, libcard/libapi); deleted by 2e
    Content\        VS.Content       loaders for Native\data\ (glTF, PNG, JSON, WAV), AssetId registry, AsyncLoader,
                                     catalogs, schema validation, patch layers; disc decoders (VS.Extract only)
                    Legacy\          T-shims for libcd/libds
                    schemas\         *.schema.json (versioned, committed)
                    patches\         our fixes/enhancements as patch layers (committed)
    Game\           VS.Game          one folder per module under src\ and include\:
                    Boot\  Title\  Field\  Battle\  Actors\  Items\  Menu\  Event\  Effects\  Ending\  State\
    Desktop\        VS.Desktop       executable: main loop, config, CLI (--replay, --capture)
    Tools\Extract\  VS.Extract       CLI: disc → Native\data\ (JSON catalogs, glTF, PNG, WAV/FLAC, AV1 MKV) + manifest + round-trip validation
    Tests\          VS.Tests         unit tests (Core.Math, decoders, catalogs round-trip, replay hashes)
    data\           (git-ignored)    ALL converted disc content, produced up front by VS.Extract. See ASSET_PIPELINE.md
  THIRD_PARTY.md    licenses of vcpkg dependencies and any lifted CC0/MIT code
  tools\            ledger\ (generators), port\ (copy tool), scaffold\ (solution generator), lint\ (boundary checks)
  Docs\             BUILDING.md (clone → build → extract → play), plan, inventory, ledgers, per-system design notes
```

Includes are written `"<System or Module>/<File>.hpp"`: `"Core/Log.hpp"`, `"Render/Device.hpp"`, `"Boot/GameApp.hpp"`,
`"Content/Disc.hpp"`. Engine systems and game modules never share a folder name.

There is no Triage project: every function has a final location (§5 step 3 gate).

Dependency direction:
- Project references: `VS.Engine ← VS.Content ← VS.Game ← {VS.Desktop, VS.Tests}`, and `VS.Extract` uses Engine and
  Content.
- Engine's Movie and Save read content, so `VS.Engine` sees Content's headers without a project reference. The
  executables link both static libraries.
- Inside `VS.Engine`, systems follow `Core ← Platform ← {Render, Audio, Input, Movie, Save}`. Game modules talk to
  each other through `Game\State` and module headers, never through another module's globals.
- Both rules are checked by lint (`tools\lint`), since a single project cannot enforce them through references.

## 4. Ledgers: the source of truth

The owner requirement is a VERY detailed list of what is done and not done. The ledgers are that list. They are **generated from the decomp** (so nothing is missed) and **hand/agent-filled** for status (preserved on regeneration).

Numeric counts below include historical snapshots. Regenerate and record the revision before using counts as a
completion claim. The EC audit records subsystem architecture debt that function/SDK name counts alone cannot detect.

### 4.1 FUNCTION_CATALOG.csv (master list)

| Column | `yes` means |
|---|---|

### 4.4 DATA_LEDGER.csv

Generated by `tools\ledger\build_symbol_ledgers.py` from `build\port\data.json`. There is one row (`G#####`) per
**storage identity**, not per spelling: a file `static`, a function-local `static`, an overlay's `D_` extern and a
shared-header table instantiated in several overlays are all separate pieces of storage, even when they share a name.
That gives 2,174 identities from 1,751 spellings (916 still generic). Each row carries the generator's
`proposed_disposition` and `proposed_system` (the majority system of its referencing functions); the naming pass fills
`disposition`, `final_name`, `final_location`, `purpose` and `confidence` ([NAMING_CONVENTIONS.md](NAMING_CONVENTIONS.md) §8).
Each row gets a `disposition`:

| Disposition | Meaning |
|---|---|
| `catalog` | It is game content (item stats, enemy tables, text, effect params). VS.Extract converts it from the user's disc into a schema'd JSON catalog in `Native\data\catalogs\`, using a decoder generated from the decomp struct ([ASSET_PIPELINE.md](ASSET_PIPELINE.md) §4). It is **never committed**. |
| `constexpr` | It is engine constants (lookup tables, sin tables, layout constants). It is re-expressed as `constexpr` in code, either computed or proven equal by a test against the disc bytes. |
| `state` | It is runtime mutable state, and it becomes a member of the owning system's state struct. |
| `asset` | It is a reference to graphics/audio, and it becomes an `AssetId`/handle into `Native\data\`. |
| `drop` | It is hardware buffers, OTs, packet pools and anything else that has no meaning natively. |

- The disc has 331 code files (`*.PRG`, `PLG*.BIN`, `EFFPURGE.BIN`). Of these:

## 6. Per-system designs

Each system lists: responsibility, API sketch, ledger rows it absorbs, Phase 1 work, Phase 2+ work and tests.
These are target designs, not an implemented-feature inventory. See §0.2 and the EC audit for current behavior;
§14 specifies the migration steps, dependencies and evidence needed to claim implementation.

### 6.1 Core (`Engine\Core`)
- **Responsibility:** fixed-point math, random, timing, logging, assertions, memory arenas, typed handles.
- **API:**
  - `Fixed12` (4.12) and `Fixed16`;
  - `Vec3s`, `Vec3i`, `Mat3x3s`, `Transform`;
  - `RotTrans`, `RotTransPers`, `NormalClip`, `AverageZ`, `Project`, with explicit rounding that matches the original where gameplay depends on it;
  - `Random` (reproduces the original `rand` LCG sequence for replay parity);
  - `FrameClock` (logical ticks; the original's field-based 60/30/20 fps steps).
- **Absorbs:** libgte (41 symbols, 1,489 uses), libc/crt, libetc VSync, `Core.Math` (41 rows), `Core` (44 rows).
- **Tests:** a math oracle against the PsyCross GTE and ps1-tests GTE vectors; LCG sequence; transform round-trips.

### 6.2 Graphics (`Engine\Render`)
- **Responsibility:** everything visible. The game submits *what* to draw, and the backend decides *how*.
- **Model:**
  - `RenderQueue` per frame. Draw items carry a `SortKey { layer, depth, sequence }`, which replaces OT index + `AddPrim` order. Reverse-depth ordering is reproduced by the key, not by a linked list.
  - Draw items: `Triangle/Quad` (flat, gouraud, textured, textured-gouraud), `Sprite`, `Tile`, `Line`, `Fill`.
  - Materials: `BlendMode { Opaque, Half, Add, Sub, AddQuarter }`, `TextureRef`, `Palette`, semi-transparency flags.
  - **Texture page space:** the original data refers to textures by tpage/clut coordinates. `Engine\Render` keeps a *logical* 1024×512 texture-page space that maps those coordinates to real GPU textures and palettes. It is a lookup structure (rect → texture + palette), not emulated VRAM. TIM uploads (`LoadImage`) register textures in that space.
  - **Capture API:** `Capture(rect) → TextureHandle` replaces `StoreImage`/`MoveImage` readbacks (title menu background, screen effects, battle transitions).
  - Display: `SetDisplayArea`, `SetClearColor`, fades, letterbox, all as typed calls.
- **Absorbs:** libgpu (78 symbols, 1,742 uses) via `Legacy\gpu_*.cpp` shims, then migrated; `Graphics` (121 rows).
- **Phase 1:** native resolution 320×240 (and the 512/640 modes the game uses), point sampling, affine mapping, dithering optional. Parity first.
- **Phase 2:** resolution scale, widescreen, perspective-correct mapping, sub-pixel vertices, 60 fps interpolation (the queue stores previous transforms).
- **Tests:** capture comparison of title, menu and first room against DuckStation reference images with a tolerance metric.

### 6.3 Audio (`Engine\Audio`, `Audio::Seq`)
- **Responsibility:** music, SFX, voice/XA streams.
- **Model:**
  - `SampleBank` holds 16-bit PCM loaded from `Native\data\audio\samples\*.wav` (ADPCM was decoded by VS.Extract) and its instrument data from `audio\banks\*.json`.
  - `Voice` holds pitch, ADSR envelope and volume/pan, emulated *behaviorally* at the envelope level, not at the register level.
  - `Mixer` runs at 48 kHz with float mixing.
  - `Reverb` presets are equivalent to the original modes.
  - `StreamPlayer` plays the FLAC streams converted from XA.
- **Sequencer:** the decomp's AKAO sequence interpreter (in `Audio`, 254 rows) is copied and becomes `Audio::Seq`. It drives `Voice`s directly instead of SPU registers, and it reads the decoded `*.seq.json` event lists (music stays sequenced, D18).
- **Absorbs:** libspu (36), libsnd (2) via `Legacy\spu_*.cpp` → migrated.
- **Phase 2:** better resampling, optional interpolation modes, volume channels, replacement music hooks.
- **Proposal (pending owner review):** instruments exported as SFZ + WAV and played by sfizz, driven by our ported AKAO sequencer through MIDI-style events; SDL3 output; tuned algorithmic or computed-IR reverb ([PORTING_WATCHLIST.md](PORTING_WATCHLIST.md) §4).
- **Tests:** sequence-event traces versus a reference capture; ADPCM decoder versus known vectors.

### 6.4 Video (`Engine\Movie`)
- **Responsibility:** FMV playback (the movies in `TITLE.STR`, converted to `Native\data\movies\*.mkv`).
- **Model:** libwebm demuxes the Matroska file, dav1d decodes AV1 to YUV planes that a shader converts on an SDL3 GPU texture, and the FLAC audio goes through `Audio::StreamPlayer`. Presentation is clocked to the audio. VS.Extract does the STR → AV1 conversion up front with ffmpeg (extract time only; [ASSET_PIPELINE.md](ASSET_PIPELINE.md) §6.7).

## 8. C vs C++

### 8.1 Why C++ (answer to the owner's question)

The decomp stays as a reference in C, so the port gains nothing from staying in C. C++23 gives:

| Benefit | Detail |
|---|---|
| Type safety for IDs | `enum class`, `Handle<T>`, `ItemId` instead of `u_char`, which also removes the 255 cap |
| Value types with operators | `Fixed12`, `Vec3`, `Mat3` (the GTE replacement reads like math) |
| RAII | Textures, files, voices and loaders clean themselves up, with no leak paths through module resets |
| Real containers | `std::vector`, `std::span`, `std::array`, flat maps, instead of fixed arrays plus counters |
| Compile-time checks | `constexpr` tables, `static_assert` on formats, `consteval` validation of constant data |
| Namespaces/classes | Map 1:1 onto systems and modules, with no `vs_battle_` prefixes |
| Variants/visitors | Draw items, effect kinds, event commands |
| Exceptions-free error handling | `std::expected` for decoders and loaders |
| Testability | Systems are objects that can be built in isolation |

Costs: compile times (mitigated by PCH and static libs), and the temptation to over-abstract (mitigated by "data for parameters, code for behaviors").

### 8.2 Promotion checklist (`.c` → `.cpp`, sets `cpp = yes`)
1. Rename the file, and fix C-only constructs (implicit `void*` casts, designated-initializer order, `restrict`, VLAs).
2. Move it into `namespace VS::<System>`. Free functions become methods where they operate on one state object.
3. Replace raw IDs with typed IDs/handles, and fixed arrays with `std::array`/`std::span`.
4. No remaining shim calls (`modernized = yes` is a prerequisite).
5. Full warning set (`-Wall -Wextra`, warnings as errors) is clean.
6. Passes a test or canonical-state replay/reference check for the migrated behavior; attach evidence before closure.

## 9. Data contracts & patterns

### 9.1 Def vs Instance (Type Object pattern)
The original mixes the two. For example, `vs_main_inventoryBlade` stores `u_char id` plus the mutable DP/PP and bitfields in one struct. We split them:

```cpp
struct BladeDef {                 // immutable, from catalog
    ItemId id;                    // "blade.scramasax"
    TextId name, help;
    BladeCategory category;       // Dagger, Sword, ...
    DamageType damageType;        // Blunt, Edged, Piercing
    Material defaultMaterial;
    int16_t str, intel, agl;
    int16_t range, risk;
    uint16_t maxDp, maxPp;
    std::vector<GripCategory> compatibleGrips;
    ModelRef model;
};

struct BladeInstance {            // mutable, lives in GameState / save
    Handle<BladeDef> def;
    Material material;
    uint16_t dp, pp;
    ClassAffinities classAffinity;   // human, beast, undead, ...

};
```

### 9.2 String IDs → runtime handles
- Catalogs and saves use **stable string IDs** (`"blade.scramasax"`, `"enemy.minotaur"`, `"room.wine_cellar.entrance"`).
- At load, a `Registry<T>` interns them into dense `Handle<T>` (a `uint32_t` index) for O(1) lookup. Code uses handles, and data and saves use strings.
- Phase 1 also records the **original numeric ID** (`legacyId`) on every Def, so that copied logic and `.mcd` import still work.

### 9.4 Schema rules (from DW4 `schemas\README.md`)
- Every file has `"schema_version"`. Loaders accept known versions only, and migrate forward (never downgrade).
- Validation at load: types, ranges, references (every `ItemId` resolves), uniqueness. Errors name the file, the JSON pointer and the rule.
- After validation, data becomes **immutable** typed records (frozen registries).
- Converted payloads (`Native\data\`) are git-ignored. Only the schemas, the extractor and the patches are committed. See [ASSET_PIPELINE.md](ASSET_PIPELINE.md).

### 9.6 Patch layers (mods)
Load order: `Native\data\` (converted from the disc) → `Native\Content\patches\` (our fixes/enhancements) → `mods\<name>\` (user). Mods may also replace converted assets (glTF, PNG, WAV, sequences, movies) by path.
Patch operations: `add`, `replace`, `merge` (field-level), `remove`, by ID. A conflict report lists every ID that more than one layer touched.

### 9.7 Behaviors stay in code
Catalogs hold **parameters**. **Behaviors** (AI routines, effect kinds, event commands, break-art scripts) are C++ registered by name in a `BehaviorRegistry`. Data refers to behaviors by name (`"ai": "ai.minotaur"`). New behaviors are added in code in Phase 3a, or in the script layer in 3b.

### 9.8 Phase 1 parity rule
Phase 1 catalogs must reproduce the original **exactly**. A round-trip test decodes the disc table, serializes it to the catalog, loads the catalog and compares field-for-field with the original values. Enhancements go into patch layers, never into the base catalog.

### 9.9 Determinism
Fixed-step simulation, the original RNG sequence, no wall-clock in game logic, and no unordered-container iteration in gameplay. This enables replays (`--replay file`) and state hashes for verification.
