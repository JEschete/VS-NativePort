### C++ promotion inventory

[CPP_PROMOTION.csv](CPP_PROMOTION.csv) holds one row per owned C++ function with one
column per [§8.2 step](../plan/RETIREMENT_AND_CPP.md#82-promotion-checklist-sets-cpp--yes);
catalog `cpp` is derived from it. Per-file counts are in `build/quality/gates.md`.
`source_cpp` and `strict_clean` are measured. They hold for every owned C++ function,
which is why they say little on their own: the other four steps carry the promotion.

**Correction, not regression (#247):** 28 rows recorded `cpp=x` before this ledger: 23 audio
rows in `XaPlayback.cpp`, `SequencerOutput.cpp`, `MusicState.cpp` and `StreamPlayback.cpp`,
and 5 menu rows in `Menu/Sounds.cpp`. All were global C-ABI symbols with blank `modernized`,
in files including `Legacy/Psx.h`, so they failed §8.2 steps 2 and 4. The correction set them to `wip`;
they reached `cpp=x` again only through the promotion slices recorded in [GATE_SLICES.csv](GATE_SLICES.csv), and any
owned C++ function with an incomplete record reads `wip`.

**Limit:** callers still using the old C symbol prevent `cpp=x`. A caller may remain
copier-managed after it adopts the registered native binding; that does not make
the caller itself promoted. The generated tables above report current owned-function
promotion, including the remaining `wip`; the old 281-function #247 checkpoint is
historical, not the current inventory. `cpp=x` is not behavior verification or EC retirement: the slices' live bindings still
read the global game state named in each slice's limits, and those compatibility contracts stay open.

### Behavior verification

[VERIFY_LEDGER.csv](VERIFY_LEDGER.csv) holds one record per verification. Every `verified=x` resolves
to a passing record whose test, replay or capture references exist. Migrated records rerun the
existing unit tests in Debug and Release; gameplay and device claims in catalog notes stay historical.
A record is a reference, not a fresh run.

**Historical corrections (#249):** `verified=x` was removed from F02737, F02738,
F03604 and F03605 (`Save::MemoryCard` menu resource lifecycle) on 2026-10-31 because
the evidence then available was prose and an uncommitted local artifact. Later
resource-release and allocation-refusal tests are recorded in `VERIFY_LEDGER.csv`;
the historical marker removal is not a claim that those functions remain untested.

### Slices and retirement

[GATE_SLICES.csv](GATE_SLICES.csv) has one row per migrated slice: its ids, the bridges it retired, the EC id,
before and after consumer counts, the revision, the evidence and, in `notes`, what stays open. A slice is a bounded
migration, not whole-system promotion or EC retirement: its callers may keep the C ABI or the live bindings to global
state that the row names. [EC_BRIDGES.csv](EC_BRIDGES.csv) lists bridges per EC id; `build/quality/gates.md`
reports their consumers. The per-slice narrative that used to be here is in Git history
(`git show 215cdd4d9:Docs/ledgers/SUMMARY.md`).

### All native code compiles as C++ (owner decision, 2026-10-31)

`Native\` holds no `.c` file, assembly file or inline assembly, and `gates.py --check` fails if one returns. The 324
generated and 38 hand-written C sources compile as C++23. This is language migration, not promotion: they keep C
linkage and the relaxed settings, so their functions stay `wip` and none gains `cpp=x`, `modernized` or `verified`.

Generated files are no longer reproducible. The copy tool, which also replayed the `tools\port\cpp_adaptations.json`
conversions, read the decomp under `resources\rood-reverseWin`, and the owner removed that folder on purpose in
`6b20016f0`.
`tools\port\copy_manifest.json` now lists files not yet migrated, and those files are edited directly (owner decision,
2026-11-18; see [CPP_HEADERS.md](../CPP_HEADERS.md)). Copied code keeps C's meaning through `/J`, `-fno-finite-loops`
and `-fno-strict-return`.

### Full tidy result (#248)

does not run it. One of its 272 original findings was a real defect: `char` is unsigned in copied code (`/J`) but

For a read-only recount in PowerShell:

```powershell
$functions = Import-Csv Docs\ledgers\FUNCTION_CATALOG.csv
$functions.Count
$functions | Group-Object copy | Select-Object Name, Count
foreach ($column in 'copied','compiles','named','understood','modernized','cpp','verified') {
    $column
    $functions | Group-Object $column | Select-Object Name, Count
}
foreach ($ledger in 'DATA','TYPE','FIELD') {
    $rows = Import-Csv "Docs\ledgers\${ledger}_LEDGER.csv"
    "$ledger rows: $($rows.Count)"
}
$owned = Import-Csv tools\port\owned.csv
$owned.Count
@($owned.path + $owned.header | Where-Object { $_ } | Sort-Object -Unique).Count
.\.venv-3\Scripts\python.exe tools\ledger\gates.py --check
```

Refresh this report from the persisted ledgers after accepted ledger changes.
Do not run `build_ledgers.py` solely to refresh these numbers: that legacy
reference-inventory generator rewrites catalogs and emits a source-scan summary.
If intentionally regenerating inventories, preserve stable IDs, merged fields
and status edits, then reconcile this report against the resulting ledgers and
ownership registry. Do not infer missing gate evidence from aggregate counts.
